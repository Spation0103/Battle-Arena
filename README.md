# Battle City

Мультиплеєрний top-down шутер у браузері: canvas-клієнт, **авторитетний** Node-сервер,
**client-side prediction + reconciliation**, інтерполяція чужих сутностей, **бінарний протокол**, TypeScript.

## Запуск

```bash
npm install
npm run dev          # http://localhost:3000  (клієнт перезбирається автоматично)
npm test             # 11 тестів: протокол, симуляція, бої, повний цикл через WebSocket
npm run build && npm start
```

Керування: WASD/стрілки, миша — приціл, ЛКМ/пробіл — постріл, **P** — вимк/увімк prediction.
Щоб відчути мережу: відкрийте `/?lag=200` (імітація 200 мс RTT) і порівняйте рух із prediction та без нього (P).

## Архітектура

```
src/shared/   constants, map, sim (детермінований крок руху), protocol (бінарні кодеки)
src/server/   game.ts (авторитетна симуляція 60 Гц), server.ts (HTTP+WS, цикл, ліміти), bots.ts
src/client/   main.ts (fixed-step цикл), game.ts (prediction/інтерполяція), render.ts, net.ts, input.ts
```

**Цикл сервера.** Фіксований крок 1/60 с (акумулятор, а не «сліпий» setInterval), snapshot кожні 2 тіки (30 Гц).
Сервер — єдине джерело істини: рух, стрільба, влучання, смерті, рахунок.

**Prediction.** Кожен тік клієнт формує команду `{seq, buttons, aim}`, одразу застосовує її локально
(`stepMove` з `shared/sim.ts` — *той самий* код, що на сервері) і шле на сервер.
Зберігає невідʼїмні команди в `pending`.

**Reconciliation.** У snapshot є `ack` — останній `seq`, який сервер застосував саме для цього гравця.
Клієнт бере позицію сервера, відкидає підтверджені команди й **повторно програє** решту.
Розбіжність (наприклад, штовханина об стіну) плавно згасає за ~100 мс; більше 120 px (респавн) — миттєвий «snap».
Позиція на сервері залежить лише від *послідовності команд*, а не від часу їх прибуття, тому джитер мережі не ламає prediction.

**Інтерполяція.** Інші гравці й кулі малюються на 100 мс у минулому між двома snapshot-ами
(годинник сервера оцінюється згладженим зсувом).

**Бінарний протокол** (little-endian, `DataView`): INPUT = 8 байт, запис гравця в snapshot = 12 байт,
кулі = 8 байт. Координати квантуються до 1/32 px у `u16`, кути — у `u16`. Повний опис — у шапці `src/shared/protocol.ts`.
Тіло snapshot кодується один раз на тік, окремо для кожного клієнта міняється лише 9-байтний заголовок.

**Захист.** Token-bucket на команди (1/тік + банк 6) — speedhack через флуд не працює;
ліміт черги, 240 повідомлень/с, `maxPayload` 512 Б, лише binary-фрейми, таймаут на JOIN, ping/pong-heartbeat,
перевірка версії протоколу, санітизація імені, `TCP_NODELAY`, пропуск snapshot для повільних клієнтів.

Сервер заповнює арену ботами до `BOT_FILL` гравців (коли людей немає — ботів немає).

## Деплой на публічний URL (Fly.io, ~5 хвилин)

Потрібен процес, що довго живе й тримає WebSocket — Vercel/Netlify serverless не підійдуть.

```bash
# 1) один раз: встановити flyctl і увійти
curl -L https://fly.io/install.sh | sh
fly auth login

# 2) у теці проєкту: змініть `app` у fly.toml на унікальну назву, потім
fly launch --no-deploy --copy-config --name <ваша-назва>
fly deploy

# 3) готово: https://<ваша-назва>.fly.dev
fly logs        # логи
fly status      # стан
```

TLS завершується на проксі Fly, клієнт сам обирає `wss://` на https-сторінці.
Стан гри в памʼяті → тримайте **один** інстанс (`fly scale count 1`). Альтернатива — `render.yaml` (Render → New → Blueprint).

Змінні середовища: `PORT`, `HOST`, `BOT_FILL` (типово 4), `STATIC_DIR`.

## Windows `.exe` (один файл, без встановлення Node)

```bash
npm run build:exe        # -> release/neon-arena.exe (Node SEA, ~87 МБ)
```
Усередині — Node, сервер, `ws` і клієнт. Запускає **лише хост**; інші заходять у браузері за посиланням.
Збирається на будь-якій ОС: `node.exe` береться з npm-пакета `node-win-x64` тієї ж версії, що й локальний Node.

## Що далі
- **Lag compensation** для влучань (зараз куля перевіряється в поточному стані сервера).
- Прогноз пострілу на клієнті, дельта-snapshot-и та interest management для >50 гравців.
- Кілька кімнат/шардів, тач-керування, сталий рейтинг.
